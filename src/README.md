# Insurance Policy Renewal System

Spring Boot REST application for managing insurance policies, renewal reminders, notification retries, dead-letter recovery, and operational reporting.

## Technology Stack

- Java 21
- Spring Boot 4.1.1
- Spring Web MVC
- Spring Data JPA and Hibernate
- Spring Batch
- H2 database
- Maven

## Prerequisites

- Java 21 or later
- Maven 3.8 or later, or use the included Maven wrapper

Check the installed versions:

```bash
java -version
mvn -version
```

## Build and Run

Using Maven:

```bash
mvn clean package
mvn spring-boot:run
```

Using the Maven wrapper:

```bash
./mvnw clean package
./mvnw spring-boot:run
```

On Windows:

```powershell
.\mvnw.cmd clean package
.\mvnw.cmd spring-boot:run
```

The application runs at:

```text
http://localhost:8080
```

## Configuration

Configuration is in `src/main/resources/application.properties`.

Important settings:

```properties
spring.datasource.url=jdbc:h2:file:./data/insurancedb
spring.datasource.username=sa
spring.datasource.password=
spring.jpa.hibernate.ddl-auto=update
server.port=8080
report.directory=D:/Projects/insurance/reports
```

If `report.directory` is not configured, reports are written to a `reports` directory relative to the application working directory.

## REST API

### Create a policy

```http
POST /policies
Content-Type: application/json
```

Example request:

```json
{
  "holderName": "Alex Johnson",
  "email": "alex.johnson@example.com",
  "phone": "9876543210",
  "policyType": "HEALTH",
  "premiumAmount": 12500.00,
  "startDate": "2026-01-01",
  "endDate": "2026-12-31"
}
```

The policy number is generated by the application. The initial status is `ACTIVE` when the end date is not before the current date; otherwise it is `EXPIRED`.

Successful response:

```json
{
  "message": "Policy created successfully"
}
```

Validation includes required fields, email format, ten-digit phone numbers, positive premium amounts, valid policy types, and a start date before the end date.

### Get policy details and notification history

```http
GET /policies/{policyNumber}
```

The response includes policy details and notification history containing the event ID, channel, reminder tier, event time, and notification outcome.

### Renew a policy

```http
PUT /policies/{policyNumber}/renew
Content-Type: application/json
```

Example request:

```json
{
  "endDate": "2027-12-31"
}
```

Policies with status `EXPIRED` or `RENEWAL_DUE` can be renewed during the fifteen-day grace period. Renewal changes the policy back to `ACTIVE`, records renewal history, and removes pending outbox reminders for that policy.

### List dead-letter records

```http
GET /dlq
```

Returns notification records that reached the maximum retry count. Each record includes the DLQ ID, original event ID, policy number, channel, reminder tier, retry count, last error, and move time.

### Requeue a dead-letter record

```http
PUT /dlq/{id}/requeue
```

The identifier can resolve the DLQ record ID or the original outbox event ID. A new `PENDING` record is inserted into `REMINDER_OUTBOX` with retry count `0`, and the DLQ record is removed.

Successful response:

```json
{
  "message": "The entry has been requeued successfully"
}
```

Requeueing an already moved or unknown record should return a not-found response with:

```json
{
  "message": "Record not found"
}
```

## Renewal Reminder Processing

The renewal detection job scans eligible policies and creates reminder records in `REMINDER_OUTBOX`.

Reminder tiers:

- `THIRTY_DAY`
- `FIFTEEN_DAY`
- `SEVEN_DAY`
- `OVERDUE`

For each eligible reminder, email and SMS outbox records can be created. Duplicate policy, tier, and channel combinations are skipped.

Active policies that receive a reminder are moved to `RENEWAL_DUE`. Expired policies beyond the grace period are moved to `LAPSED`.

## Notification Processing and Retries

Pending outbox records are processed by the notification dispatch flow. Each attempt is recorded in `NOTIFICATION_LOG`.

Possible outcomes:

- `SENT`: the outbox record is removed.
- `FAILED`: the retry count is increased.
- `GATEWAY_TIMEOUT`: the retry count is increased.

After three failed attempts, the event is moved to `REMINDER_DLQ` with the last error and retry count, and the outbox record is deleted.

Requeued DLQ records start a new processing cycle with retry count reset to zero.

## Scheduled Jobs

Scheduling is enabled by `@EnableScheduling`.

| Job | Schedule | Purpose |
|---|---|---|
| Renewal detection | Every minute at second 0 | Detect eligible policies and create reminders |
| Notification processing | Every minute at second 0 | Process pending outbox records and apply retries |
| Daily report | 00:05 daily | Generate the previous day's report |

The notification job also generates a report for the current date after processing, so a report can be created without waiting until midnight.

Spring Batch job definitions are also present for renewal detection and notification processing. Automatic Spring Batch startup is disabled by:

```properties
spring.batch.job.enabled=false
```

## Daily Reports

Reports are CSV files written to the configured report directory:

```text
reports/daily-report-yyyy-MM-dd.csv
```

The CSV contains:

- Policy counts for `ACTIVE`, `RENEWAL_DUE`, `RENEWED`, and `LAPSED`
- Notification counts grouped by reminder tier
- `SENT` notifications
- `FAILED` notifications with their outcome/reason
- `GATEWAY_TIMEOUT` notifications
- `DEAD_LETTERED` records grouped by reminder tier and DLQ error

Example columns:

```text
report_date,section,tier,status,reason,count
```

Renewals are tracked in `POLICY_RENEWAL_HISTORY` so that `RENEWED` counts are based on the selected reporting period rather than only the current policy status.

## Renewal Summary Logs

The latest renewal detection summary is stored at:

```text
logs/renewal-detection.log
```

The file contains the latest complete summary:

```text
Renewal Detection Summary
Policies Scanned
30 Day Reminders
15 Day Reminders
7 Day Reminders
Overdue Reminders
Skipped Already Reminded
```

Before a new summary replaces the active file, the previous summary is retained as a timestamped file in the same directory:

```text
logs/renewal-detection-yyyy-MM-dd-HH-mm-ss-SSS.log
```

## Main Database Tables

- `POLICIES`: policy details and current status
- `REMINDER_OUTBOX`: pending notification work
- `REMINDER_DLQ`: notifications that exceeded three attempts
- `NOTIFICATION_LOG`: notification attempt history
- `POLICY_RENEWAL_HISTORY`: renewal events and timestamps

## Error Handling

The application provides centralized REST error handling for:

- Validation failures
- Invalid request bodies and enum values
- Missing policies
- Duplicate customers
- Duplicate DLQ requeue attempts
- Missing DLQ records

Responses use a JSON message format where applicable:

```json
{
  "message": "Error message"
}
```
